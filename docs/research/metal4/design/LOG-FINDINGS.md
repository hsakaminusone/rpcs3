# Metal 4 run-log findings — Ridge Racer 7 (`BLUS30001`)

**What this document is.** The objective results of the Metal 4 investigation, open items first.
`L<n>` ids are stable because other documents cite them; resolved rows are compressed, not deleted.

**Method.** Probe log, RPCS3 log and crash reports; bounded captures. Probe levels: 2 = counters,
3 = per event, 5 = per draw + dumps. A window is armed by a cubemap bind, a large B8 bind, or
`MTL_PROBE_AT_SEC`, and now probes at most 64 draws (L113). Every number is measured unless the row
says *hypothesis*.

**Artifacts.** Run 1 `/tmp/mtl4-final.log` (183 919 lines, 5 windows, exit 0 at 414 s). Run 2
`/tmp/mtl4-noalpha.log` (16.4 MB, 3 windows, quit at 4:21 after the queue wedged, L113). Dumps
`/tmp/mtl4-dump/`; `/tmp/analysis.txt`, `/tmp/rpcs3-stall.txt`; `~/Library/Caches/rpcs3/RPCS3.log`.

**States.** `open` · `fixed` (code changed) · `settled` (measured, no action) · `folded`.

## 1.2 FIFO desync and the freeze

Closed by L145 and run U (2026-10-27). The class had one mechanism with an exact proof: **a guest
data word read as a command header.** GET left its command boundary, the word it landed on was an
argument, the malformed-command branch reported the desync, and recovery restored GET to that same
word, so it never advanced (L117–L121). The last half was the acknowledgement: GET published the
prefetched block end and licensed the guest to recycle the chunk the parser was still in. Run U
made 2,892 handovers with no desync, no read-ahead and no `Dead FIFO`; the visual defects in §1.1
are unchanged and are not a FIFO symptom.

The 2026-10-25 diagnostic run moved the cause one level up. The parser's own bookkeeping is intact
for the whole run (L124), and the geometry of the producer is now measured (L122). The guest
ping-pongs between two command buffers and alternates `put` between them, so `put` names the buffer
the parser is *not* reading (L123). The one frontier event that layout creates is the move itself:
the parser waits on `put`, the app moves it to the other buffer, and the parser resumes on the word
it was waiting at (L125). In the failing frame that resume led, through a link in the published
chunk, into the other buffer at `0x2B0C` past its published end (L126). The word there was guest
data (L127). The probes could not see it because every numeric test in them assumes the frontier is
numerically ahead, and here the buffer being read has the lower address (L130).

The second 2026-10-25 run gave the exact frontier shape (L132). At 2:36.587 the parser is parked at
`A+0x2840`; the app moves `put` to `B+0x8CC` and the word at the parked position is still
`0x00010000`, i.e. not written for this pass. That is a **wait**, not a walk. At 2:36.620 the app
moves `put` to `A+0x28CC` in the *same* stream and writes the command at the old frontier; the
parser resumes and immediately hits the second, distinct failure: `pos == put == A+0x28CC` and the
word there (`0x434c2587`) comes out of the cache. The cache was filled to `PUT | 0x7f` and the old
`addr < put` trim only ran when `addr < put`, so the word **at** PUT bypassed the `put == addr`
check. The fix is a per-stream published frontier, an exact cache bound and packet atomicity
(L132).

The third 2026-10-25 run (`run C`) and the fourth (`run D`, 22:17) have the same boot stall, and the
park probe in run D corrects the first reading. The boot chunk is published to `0xcb09d4`; the
parser enters the `CALL 0` at `0xcb0634`, returns, and stops at `0xcb09d4`. In run D the word there
is `0x0`, so it is **not** the published link: the parser is correctly waiting for the producer's
next chunk. The old `put == addr` early return was still a real hole for the healthy case where PUT
names the link (run B's 23.220 jump), and L133 removes it, but it did not cause this stall.

Runs E–H (2026-10-25) first suggested the labels belonged only to init: the two
`BACK_END_WRITE_SEMAPHORE_RELEASE` labels (`0x60300800`, value `0x01000000`) fired before the boot
chunk was published, and no release appeared at the park. Run K (2026-10-26) captured the boot
chunk tail before it was recycled and corrects that: the last method before the link is a non-flip
`NV4097_BACK_END_WRITE_SEMAPHORE_RELEASE` (`0x75c`) to `0x60300800` with `0x1`, and the next
`NV406E_SEMAPHORE_ACQUIRE` at the same address has arg `0`. The release is staged and committed
(L134), but the acquire reads the old `0` before the GPU copy runs, takes the `sema == arg` fast
path, and the parser parks on the genuine `0` link. L134 is a real fix but not sufficient: the
acquire needs a targeted wait for the label it is acknowledging (L135).

Runs H and I have the same park: `frontier=put=0xcb09d4`, `word=0x0`, `get=0xcb09d4`, and
`cache=0xcb0980+0x3d4`. The cache is **not** oversize: the entry condition ran against the
previous cache `0xcb0600+0x3d4`, which ends exactly at the frontier; the park line prints the
new line base (`0xcb0980`) with the old size. The word at the frontier is a live read, and it is
`0x0`, so the parser is correctly waiting for the producer. The cache/GET lead is therefore
closed; the open question is what releases the producer. The next run captures the chunk at the
jump into `0xcb0000`/`0x10a0000`, before the producer recycles it, so the final methods are not
lost as they are in the parked, zeroed tail. The black picture is still the L12 FMV; the producer
stall is what keeps 3D from starting.

Run L (2026-10-26) closed the next question: the acquire wait works, but the guest word is still
`0`. The label page (`0x60300000`, the RSX reports) is mapped at 18.96 s, while the Metal device
and its 4 GiB no-copy guest import are created at 4.58 s; RPCS3 replaces guest ranges with
file-backed `MAP_FIXED` mappings. A standalone Metal 4 experiment shows the consequence: a GPU
copy into a page that was re-mapped **after** the import was created is not visible to the CPU,
while a copy into a page mapped **before** the import lands normally (and an import created after
the remap reads the value). The import is fixed at creation, so the label write went to the old
physical page. That is L136. The fix, L137, gives each label page its own small import, created at
the first release that targets it and cached for the process: the GPU writes the page the CPU
reads, with no drain and no per-frame cost after the first. A same-command-buffer readback
(`gpu=`) and the acquire's post-sync word remain in the build for the confirming run.

Run T (2026-10-27) named the last half of the class. The parser did not lose the link to a cache or a numeric test:
**GET had already told the guest that the chunk was free.** `sync_get()` published the end of the
prefetched block, the guest recycled A while the parser was blocked for 188 ms in the label
acquire, and the link at `A+0x9d4` became the next chunk's data before the parser arrived (L144).
The L141/L144 publish samples only narrowed the window; the window is the chunk. `sync_get()` now
publishes `m_fifo_pos`, the executed position, and `cellGcmCallback` writes the jump before it
publishes PUT. The sample layer is gone, and the stream frontier is enforced in the fast mode as
well as the accurate mode (L145).

The 20 ms figure is therefore not the steady-state acquire cost; it is the shape of the tail. The
correct comparison is not "Metal acquire is slow", it is "Metal has an unbounded CPU wait on the FIFO
thread and VK does not". The parser is the FIFO consumer: any window-server stall on the RSX thread
shows up as a guest command-buffer stall, and in RR7 a stalled parser is also what turns a normal
buffer switch into the L142 deadlock. The fix is to take the window server off that thread, not to
make `nextDrawable` faster. Two designs preserve the current renderer:

1. **Offscreen compose plus a present thread (recommended).** The RSX thread composes the frame into
   a small ring of offscreen textures, signals a shared event, and returns from `flip` immediately.
   A dedicated present thread owns `nextDrawable`, `waitForDrawable`, the final blit and `present`;
   if the drawable pool is dry it drops the oldest composed frame instead of stalling. The RSX
   thread's only new cost is an atomic publish, and the FIFO never waits on the window server. This
   is the same split VK gets for free from `vkQueuePresentKHR`, made explicit.
2. **Bounded acquire on the RSX thread.** Set `allowsNextDrawableTimeout` and skip the acquire when
   the in-flight drawable count is at `maximumDrawableCount`, so `nextDrawable` is never called on a
   dry pool; move `m_queue->wait(drawable)` to a GPU timeline event or to the present path. This is a
   much smaller change but still couples the parser to the pool, and the frame-drop policy becomes
   visible as judder.

Until either lands, the measured steady-state cost is dominated by `frame/gpu wait` and the feedback
wait, not by the acquire; optimizing `nextDrawable` alone would not move the parser.
